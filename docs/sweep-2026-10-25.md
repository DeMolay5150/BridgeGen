## 1. Succession-readiness scoring engines (`lib/simulator`, `lib/explain`)

Probed with hostile inputs: >6× existing leverage, loss-making companies, 0% / 100% founder stakes, full transfer, NaN and Infinity.

| # | Defect (reproduced) | Fix | Files |
|---|---|---|---|
| E1 | **"No change" wasn't neutral above 6×.** A company with $1M EBITDA and $10M debt showed a forced $4M paydown in its *Today* baseline, because the neutral leverage was clamped to the 6× slider max. Every module (simulator, fork, red team, report, deck, alerts, matrix) anchors on Today. | `leverageRange(baseline)` stretches the bound to the company's real leverage. The engine, the explainer and both slider surfaces use it, and `currentLeverage` is no longer clamped. | `lib/simulator/defaults.ts`, `engine.ts`, `lib/explain/simulator.ts`, `components/simulator/scenario-controls.tsx`, `components/present/presentation.tsx` |
| E2 | **An outside CEO's "uplift" deepened losses.** With −$2M EBITDA and +20% uplift, the result was −$2.4M. | `ceoImprovement()`: the uplift is \|EBITDA\| × uplift, so it narrows losses. The explainer says "narrows losses by…" and calls the same function, so it can't drift. | `engine.ts`, `lib/explain/simulator.ts` |
| E3 | **NaN read as the worst case.** `clamp(NaN)` returned `min`, turning a NaN EBITDA into a −$10B loss. | NaN falls back to the in-range value nearest zero. | `lib/simulator/defaults.ts` |

Checked and sound: ownership always sums to 1 (including 100% founder with full transfer); every output is finite under the existing hostile sweeps; the governance score's maximum is exactly 100; the Red Team shocks are bounded and finite.

**Design gap, not fixed (needs a product decision): multi-heir ownership.** The engines model the next generation as one holder (`Holders.nextGen`). Consequences:
- The successor-exit shock buys out the *entire* heir stake, which is the worst case for N heirs.
- At 100% transfer it borrows to buy out the company's sole owner.
- Per-heir stakes, unequal splits, active versus passive heirs, and the dilution of a single successor's control aren't representable.

Supporting N heirs touches the engine types, persistence schema, explainers, Decision Room stakeholders and the UI. It needs a spec in `tasks/todo.md` before any code.

### ADR-001 (accepted 2026-10-25, stages 1–3 built): modelling several heirs

- **Context:** `Holders.nextGen` is a single stake. Successor exit buys out all of it, control shift compares the combined heir stake with the founder, and the room has one heir seat. Real families have several heirs, active and passive, and their disagreements with each other are the main risk.
- **Option 1:** keep one bucket and add `heirCount` and `concentration` parameters. Cheap, but it can't say *which* heir leaves, and the explainers get vague.
- **Option 2 (recommended):** `Scenario.heirs: { id, name, share, active }[]`, with `Holders.nextGen` derived as the sum so every existing consumer keeps working.
  - Successor exit buys out one named heir (by default the largest active one), and dispute risk scales with the heirs who remain.
  - Control shift fires when any one heir out-owns the founder, plus a deadlock caution when the top heirs tie with no majority.
  - Alignment averages heir support weighted by stake and adds a dispersion sub-score.
  - Saved rows default-merge to one heir with share 1, so every saved company simulates identically (lock that with a snapshot test). No SQL migration is needed.
  - About 15 files (engine, red team, projection, explainers, narrative, report, deck, persistence schemas, UI); per-heir Decision Room seats can come in a later phase.
- **As built (2026-10-25):** heirs live on the **baseline** (`Baseline.heirs`), not the scenario. They describe the family, not a decision, and a scenario field would be reset every time a Fork branch or strategy preset rebuilds its scenario. `lib/simulator/heirs.ts` normalizes the list (missing = one unnamed heir); `SimulationResult.heirs` gives each heir's ownership, equity and recap cash. Signals: `control-shift` names the heirs who out-own the founder, `heirs-bloc` when only the heirs together do, `heir-deadlock` when the top two tie without a majority. Successor exit buys out the largest active heir (else the largest) and scales the dispute discount by 1 + 25% per remaining heir (up to three). UI: heir editor in the baseline panel, heir-by-heir rows under ownership. `heirs.test.ts` proves saved companies without heirs simulate, stress-test and project identically. Stage 4 was built on 2026-10-26; see the next bullet.
- **Stage 4 (built 2026-10-26, branch `feat/2026-10-26-followups`):**
  - **Alignment:** `scoreScenario` scores each heir with a stake. An heir in the business uses the Next-gen priorities; one outside it weighs succession as cash to shareholders (`heirPriorities`). Next-gen support is the stake-weighted mean, and the disagreement spread counts every heir as a seat, so a split family lowers alignment. One default heir scores identically (test).
  - **Room seats:** each named heir gets their own private link, stored as the seat `nextGen:<heir id>` in the existing `stakeholder` column (`lib/room/seats.ts`). Migration `20261026090000_heir_seats.sql` only widens the CHECK, so keys, link binding, RLS and grants are unchanged and old code keeps working. Invited or answering heirs replace the shared next-gen seat in gap detection (it stays if it has answers); the founder's predictions are checked against each next-gen seat. The server returns seat ids only; the browser names heirs from the baseline, and an heir's own link greets them by name.
